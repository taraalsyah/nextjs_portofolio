1 Status Lifecycle & Task States

Dalam sistem Task Management Next.js ini, Task memiliki 5 status resmi yang terdefinisi secara ketat dalam database Prisma Schema. LOCKED bukan merupakan status task, melainkan kondisi independen (isLocked === true).

Status Definisi Domain Syarat Transisi Valid Kondisi Lock
BACKLOG Task baru dibuat dalam tahap perencanaan awal. Dapat berpindah ke OPEN atau IN_PROGRESS Editable
OPEN Task aktif yang siap diambil atau ditugaskan ke member. Dapat berpindah ke IN_PROGRESS Editable
IN_PROGRESS Task sedang dikerjakan secara aktif oleh Assignee. Dapat mengajukan Request to Done / Request to Close Editable (selama pending status = NONE)
DONE Task selesai dan disetujui via workflow Request to Done. Dapat mengajukan Request to Close LOCKED (Read-Only)
CLOSED Task ditutup secara permanen via workflow Request to Close. Status terminal (akhir) LOCKED (Read-Only)

3 API Endpoints & State Mutation Logic
Endpoint API Method Target Mutasi State Aturan Keamanan & Otorisasi
/api/tasks/[id]/request-done POST doneRequestStatus = PENDING Hanya Assignee / Member aktif project yang dapat mengajukan.
/api/tasks/[id]/approve-done POST status = DONE
isLocked = true		 Otorisasi khusus Project Owner / Admin. Task terkunci pasca approval.
/api/tasks/[id]/reject-done POST status = IN_PROGRESS
doneRequestStatus = REJECTED		 Task kembali ke status aktif pengerjaan.
/api/tasks/[id]/request-close POST closeRequestStatus = PENDING Memicu Email Notifikasi KHUSUS ke Project Owner.
/api/tasks/[id]/approve-close POST status = CLOSED
closeReviewedById = ownerId		 HANYA Project Owner yang berhak melakukan approval.
/api/tasks/[id]/reject-close POST status = status sebelumnya Mengembalikan task ke status awal (IN_PROGRESS atau DONE).
Aturan Notifikasi Email Ketat (Request to Close):
Ketika member mengajukan Request to Close, email notifikasi WAJIB HANYA dikirim kepada Project Owner (task.project.owner.email). Sistem melarang keras pengiriman email notifikasi kepada requester, task creator, assignee lain, atau admin lain untuk menjaga kerahasiaan dan jalur komunikasi langsung.
4 Security Boundary & Task Locking Pipeline

Setiap permintaan operasi mutasi task (Update, Delete, Transisi Status, Reassign) diproses melalui Multi-Layer Authorization Pipeline di sisi Server:

1. Authentication
➔
2. Workspace Access
➔
3. Project Access
➔
4. Permission Check
➔
5. Lock Check
Ketentuan Task Locking (isLocked === true):
1. Task dengan status DONE atau CLOSED dianggap sebagai resource Read-Only.
2. Percobaan perubahan data pada task yang terkunci akan secara otomatis ditolak oleh backend server dengan respon HTTP 403 Forbidden (getTaskLockedResponse()).
3. Pengecekan otorisasi di sisi Frontend UI hanya berfungsi sebagai UX (menyembunyikan/menonaktifkan tombol) dan bukan security control utama.
5 Task Numbering & Audit Logging
  • Auto-Generated Task Number: Penomoran task dibuat secara otomatis dalam urutan atomic transaksi database menggunakan helper generateNextTaskNumber(tx) dengan format TSK-000001, TSK-000002.
  • Audit Activity Trail: Setiap perubahan status, approval, rejection, atau pengeditan field task diwajibkan mencatat riwayat aktivitas secara atomic via logTaskActivity().
  • Zero Layout Shift UI UX: Pada tabel task frontend, pengambilkan data latar belakang (*fetching*) memisahkan state isLoading dan isFetching untuk mencegah hilangnya tabel (*flicker*) saat perpindahan halaman pagination.
